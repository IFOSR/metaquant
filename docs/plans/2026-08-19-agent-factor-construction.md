# Agent 因子构建：从研报到可执行模型

日期：2026-08-19
状态：设计稿

## 1. 背景与问题

当前 `factor_extract` 让 agent 从研报中抽取**声明式因子 IR**（factor-ir/v1），
例如 `returns(close, 5)`。这种"公式"式的因子定义天生只能表达简单线性因子：

- 注册操作符只有 22 个（returns / lag / delta / rolling_* / cs_rank / zscore …）
- 研报主流的**深度学习因子**无法表达，抽取出 `model` 操作符后直接撞
  `IR_UNKNOWN_OPERATOR`
- 传统简单因子（动量、反转、低波动）的 alpha 已基本枯竭——它们现在更多
  是研报里"被中性化掉的风格暴露"，而不是"要挖掘的 Alpha"

结论：**agent 抽取的产物形态错了。** 研报给的从来不是一个公式，而是一套
构建步骤（用什么特征、什么标签、什么架构、怎么中性化、怎么训练）。

## 2. 核心判断

最难、最有价值的一步是**因子构建**——把研报的思路和步骤，转化成能实际
训练出模型的实现。而"用历史数据产生因子值 + 回测"，是通用的、简单的
环节，平台已经具备（PIT 数据 + 回测 + 验证纪律）。

```
研报（步骤+思路） → 构建模型 → 因子值 → 回测验证
     ↑ 关键，agent 该帮      ↑ 通用，平台已能做
```

平台的核心价值因此重新定位：**帮助研究员完成"研报 → 可执行模型"的转化，
并对转化产物施加纪律（冻结、可复现、PIT 安全）。**

## 3. 目标架构

agent 的产物从「不可执行的 JSON 规格」升级为「可执行的代码工件」。

```
① 研报 → agent 抽取「构建规格」
   特征集合、预测标签、模型架构思路、训练方法、中性化配置

② 规格 → agent 生成「可执行代码」
   model.py + train.py + infer.py（可审计、可冻结、内容寻址）

③ 代码 → 平台执行
   训练（可用历史数据）→ 推理（必须 PIT 安全）→ 因子值

④ 因子值 → 回测/验证（通用环节，现有能力直接复用）
   PIT 检查 → IC/稳定性/独立性 → 晋升审批
```

其中 ② 是最难、最有价值的一步，也正是 LLM 最擅长的：把"思路"翻译成
"代码"。

## 4. 代码工件设计

agent 的产物是三个内容寻址的代码工件（存 MinIO，hash 冻结）：

| 工件 | 职责 | 输入 | 输出 |
|---|---|---|---|
| `model.py` | 模型结构定义 | — | 模型类（PyTorch 或等价） |
| `train.py` | 训练脚本 | PIT 数据 + 超参数 | 模型权重工件 |
| `infer.py` | 推理脚本 | 模型权重 + PIT 数据 | 因子值（时序） |

### 4.1 数据接口

平台提供统一的数据接口，代码通过它读 PIT 数据，**接口本身强制 PIT 安全**：

```python
# train.py / infer.py 里使用
from quant_platform.ml import load_pit_frame

frame = load_pit_frame(
    snapshot_id="snapshot-cn-a-001",
    fields=["close", "open", "high", "low", "volume", "amount", "vwap"],
    decision_time="2026-08-03T07:00:00+00:00",
)
# 返回一个只含 decision_time 之前数据的 DataFrame，杜绝未来泄漏
```

训练与推理的边界由接口保证：

- **训练**：允许使用更早的历史窗口（含"未来收益"作为标签），但标签在训练
  脚本内部由数据接口的 `horizon` 参数显式声明
- **推理**：`load_pit_frame` 只返回 `available_time <= decision_time` 的行，
  模型无法看到未来

### 4.2 因子规格（agent 抽取的中间产物）

agent 第一阶段产出**构建规格**（可审计的"研究意图"），第二阶段生成代码。
规格结构：

```json
{
  "inputs": ["close", "open", "high", "low", "volume", "amount", "vwap"],
  "label": "future_21d_vwap_return",
  "architecture": "MLP / LSTM / Transformer / ...",
  "style_neutralize": ["size", "volatility", "reversal", "liquidity"],
  "expected_direction": "POSITIVE"
}
```

规格本身不可执行，但它是代码生成的输入和审计依据。

## 5. 纪律保持

"因子变复杂"不削弱纪律，反而更需要：

1. **代码冻结**：三个工件 + 规格内容寻址，预注册后不可改
2. **可复现**：同样的代码 + 同样的权重 + 同样的数据 → 同样的因子值
3. **PIT 安全**：训练可用历史数据（标签天然是未来收益），推理必须只读
   `available_time <= decision_time` 的数据——由数据接口强制
4. **审计血缘**：研报 → 规格 → 代码 → 权重 → 因子值 → 验证报告，全程
   内容寻址可追溯

## 6. 分阶段落地

### 阶段 1：agent 生成可执行代码（纯 agent，无新基础设施）

- `factor_extract` 从"抽取 factor-ir JSON"改为"抽取构建规格 + 生成
  model.py / train.py / infer.py 草稿"
- 产物直接给研究员审阅，研究员在自己的环境训练
- 不改平台执行引擎，先打通"研报 → 代码"这一最难转化

### 阶段 2：代码试运行闭环（沙箱）

- 沙箱容器执行 agent 生成的代码
- "生成 → 试运行 → 报错 → 修正"循环，直到代码能产出因子值
- 加 Python 依赖（PyTorch 等）进沙箱镜像

### 阶段 3：训练 + 推理 + 回测闭环

- 平台集成训练/推理执行，模型权重注册为工件
- 因子值进入现有验证管道（IC/稳定性/独立性/晋升）
- 形成"研报 → 代码 → 模型 → 因子 → 验证"的完整闭环

## 7. 风险与取舍

- **生成代码跑不通**：LLM 生成代码的经典问题 → 阶段 2 的试运行闭环解决，
  失败时回退给研究员人工修正
- **训练算力**：深度学习训练可能重 → 阶段 3 小模型 CPU 跑通验证，大模型
  留给研究员 GPU 环境，平台只验证因子值
- **代码安全**：沙箱执行，代码只读数据、只写工件，禁止网络/文件系统写
- **框架选择**：PyTorch 是主流但重；可先固定 PyTorch，后续支持 ONNX 等
  模型格式做推理，训练仍走研究员环境
